02

发布流程（tag，B 模式）

选定 B 模式（两段式）：tag 推送自动完成「拉取 → staging → 冒烟预检」，但不自动重启线上——应用时机由你在面板点一下（或跑一条命令）。发布语义：

git tag v1.4.1 && git push --tags │ ▼ release-watcher（gateway 内，每 5 分钟 ls-remote / GitHub webhook 即时路径） ① 变更计算 git diff --name-only <deployed_sha>..v1.4.1 + 模块 manifest → 受影响模块 ② staging tag 完整树 → ~/releases/v1.4.1/（线上不受影响） ③ 冒烟预检 node --check 全量 + 模块 /healthz 探活 ④ 等待应用 面板提示「v1.4.1 就绪：checkin +2 文件 · 应用？」← ★人工卡点 ⑤ 应用 原子切换 current 软链 + 仅受影响模块 sv restart + healthz + 冒烟 ⑥ 记账 deployed-version.json（每模块 tag/sha/时间）+ 审计 JSONL + 邮件 changelog 失败 ⟶ 自动回滚上一 release 目录 + restart + 告警邮件（秒级，无需重新上传）

回滚 = 切回上一 release 目录 + restart，常驻手机端最近 5 个 release。tag 规范：单一 v<major.minor.patch> annotated tag，受影响模块由 diff 自动推导。gateway 自身更新标记为 disruptive（全站瞬断 ~2s），面板会提示进维护窗口。

P2 待实施：release-watcher 常驻 + releases/ 目录布局 + 面板「应用/回滚」按钮。当前 P1 阶段的发布 = update-modules.ps1（工作副本部署），tag 流程接入后无缝替换。

踩坑记录（部署过程实测）

① notify.js 的巡检调度器原在 import 时启动，拆进程后会双份发告警邮件——已改为显式启动；② metrics 里 du -sh 全盘扫描 50s 是 /api 慢的存量元凶，已加 1h 缓存（连带修复，/api 46s→0.8s）；③ 冒烟清理进程必须按 CommandLine 匹配，不能全杀 node；④ PowerShell 5.1 跑 UTF-8 无 BOM 脚本会中文乱码解析失败，脚本需带 BOM；⑤ scp 的端口参数是 -P（大写），ssh 是 -p。
