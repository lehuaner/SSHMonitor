### 6.2 ★ 设备指纹 fp 算法（逐字节验证通过）
```
serialized = "&".join(f"{quote(k)}={quote(v)}" for k,v in sorted(fields))   # 空值也要保留
body       = serialized + "&cs=" + SHA1(serialized)      # ★SHA1，不是 MD5
fp         = base64( XOR(body).encode('latin-1') )        # key 初值 211，key ← 密文字节
```
- **`cs` 必须 SHA1**：改用 MD5（云空间旧版算法）→ 服务端 200 但 `sid` 返回**空串**。
- **服务端不校验各哈希字段真实性**：canvas/webgl/fonts/ep/epls 全换伪造值，只要 `cs` 对，照样签发 sid
  ⇒ **纯 Python 即可，不需要 Playwright**（这点比参考项目更省事）。
- **两个坑**：① XOR 加密/解密是**两个不同函数**（都按密文字节滚动 key），不互为自反；
  ② XOR 输出必须 `.encode('latin-1')` 再 Base64，用 utf-8 会把 744 撑到 928 并被判非法。

### 6.3 ★ hwid_cas_sid = 免验证的持久化关键
- 请求带已有值 → 服务端**原样回显**并写 `Max-Age=315360000`（10 年）cookie。
- 不带 → 每次会话新签发一个 sid（同会话幂等、跨会话不同）。
⇒ 持久化它，后续重登自带受信设备身份，**不会再触发设备验证**。这是解决"没有持续 cookie"的正解。

## 12. ★★ 推翻 §11.6 结论：WorkBuddy 存在 cookie → Bearer 换票机制（2026-09-10 16:20）

### 12.1 为什么之前判错
旧结论基于 `workbuddy_/2/3/4_解析结果`。**这 4 份抓包都没覆盖「桌面端登录握手」那一段**，
而换票端点只在登录握手时出现 ⇒ 穷举业务路径当然找不到。「bundle 里没有 Authorization」这条反证也只能证明
**web 控制台**不换票，不能证明桌面端不换。

### 12.2 换票链路（`workbuddy5_解析结果` 找到 + 实测通过）
```
① POST https://copilot.tencent.com/v2/plugin/auth/state?platform=workbuddy   （无鉴权，X-No-Authorization: true，体 {}）
   → { data: { state, authUrl } }
② POST https://www.workbuddy.cn/console/login/enterprise?state=<state>       （带站点 Cookie）
   → { data: { accessToken, expiresIn:5184000(60天), refreshToken, refreshExpiresIn:7776000, tokenType:"Bearer" } }
```
抓包时序佐证：`005` state → 登录页 → `041/054/060` 轮询 `/v2/plugin/auth/token?state=`（`code:11217 login ing...`）
→ `061` 换票命中 → `069` 轮询也拿到 → `072/074` 起请求带 Bearer。

### 12.3 实测边界（都是踩出来的）
- **最小凭证 = `session` + `session_2` 两项**。对照实验：无 cookie / 只给 session / 只给 session_2 → **全 401**；两者齐 → 200。
- **★站点会话绑定登录时的 User-Agent**：换一份同样合法的完整 Chrome UA → **401**；用登录那个 Edge UA → 200。`accept` 头无关。
  （所以之前那条「UA 不匹配就 401」的旧坑，本质是**会话级绑定**，不只是网关签名校验。）
- **可重复换票**（非一次性），但**有速率限制**：短时间连换 ~8 次开始 401，等 45~60s 恢复 ⇒ token 必须缓存。
- 换出的 Bearer 在 `www.workbuddy.cn` 与 `copilot.tencent.com` **都可用**（均 200，返回体一致）。
- `x-device-token` **非必需**；不需要请求体。
- **refreshToken 暂不可用**：`grant_type=refresh_token&client_id=console` → `401 unauthorized_client`；
  `client_id=account-console` → `400 invalid_grant`（Token client 不匹配）。⇒ 续期只能靠 Cookie 再换一次。

### 12.4 落地实现（`authMode: 'auto'`，与 Trae `resolveToken` 同构）
- 新增 `exchangeTokenFromCookie()` / `resolveCredential()`：auto 模式有 Cookie 就换 Bearer 并用 Bearer；
  剩余 < **6h** 才再换；**换票失败自动回落 Cookie 直连**（签到不中断）；失败后 **60s 冷却**（模块级 Map，不入 JSON）。
- 换出的 token 回写 `task.config.token` + `task.tokenExpiredAt`（靠调度层 `saveTasks` 落盘）。
- `authMode` 新增 `auto` 并设为**新默认**；`web` / `bearer` 旧行为不变（老任务无 authMode → 仍推断为 web）。
- `probeSession` 报**需要人工维护的 cookie** 的到期（auto 下维护的是 cookie 而非派生 token），另附 `tokenExpiresAt`。
- 换票 401 错误信息直接列三种成因（UA 不一致 / 缺 session / 换票过频）。
- 自检：`_selftest_providers.mjs` 新增 F2-a~d 共 9 项（换票触发 / 缓存复用 / 401 回落 / 冷却 / 仅 token 不换票）→ **44/44**。
- 生产：任务 `818a96d9` 由 `web` 切 `auto`（cookie 保留），`POST /api/checkin/test` → `{ok:true,total:1587.86,valid:true}`；
  Bearer 已落盘，`tokenExpiredAt=2026-11-09`。

### 12.5 结论对用户的意义
**无需再抓包**：只需粘贴一次 Cookie，服务端自动换出 60 天 Bearer。人工维护的仍是 Cookie（名义 7 天，到期前邮件提醒）。

### 12.7 方法论教训（值得复用）
判「某端点不存在」之前，先确认**抓包是否覆盖了会用到它的那个流程阶段**（登录握手 / 首次授权 / 支付确认…）。
业务流抓包只能证明「业务流里没调用过」，不能证明「该端点不存在」。
